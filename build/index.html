How I Build

Specification, architecture, and verification are mine. Implementation runs through a custom agent harness.

I build enterprise systems with AI agents. That does not mean the agents decide what to build. It means I write the specification, record the architecture decisions, decompose the work into verifiable pieces, and refuse to accept a change I have not verified. The agents write the code inside those constraints.

The rule the whole method rests on: a check you did not run is inconclusive, never a pass. Every claim on this site is held to that standard.

The loop

Six stages. Each one produces an artifact that the next stage is held to.

  1. 1

    Write the spec before the code

    An objective, explicit scope, and acceptance criteria that can be checked by a command or an observation. If a criterion cannot be verified, it gets rewritten until it can.

    I ownScope, acceptance criteria, what "done" means.
    The agent getsA written contract, not a conversation.

  2. 2

    Record the decisions

    Architecture choices with a reason, compatibility facts with a source and a date, deployment topology, data model, contracts, and measurable non-functional requirements. A fact without a source is an assumption, and assumptions get a spike task.

    I ownDecisions, tradeoffs, risk register.
    The agent getsBoundaries it may not cross.
    agents-md-example.md ↓
  3. 3

    Decompose into verifiable tasks

    Each task fits one context window and carries its own verification step. Small enough to review completely, specific enough that no judgment is required to start it.

    I ownSequence, dependencies, what can be parallel.
    The agent getsOne task, one verification command.
    verification-checklist.md ↓
  4. 4

    Hand off with a context pack

    A fresh instance gets a document written for someone with zero memory: current state, what was just completed with evidence, the single next action, what not to redo, and what not to touch.

    I ownWhat context is sufficient, and what is noise.
    The agent getsA clean starting state, every time.
    handoff-template.md ↓
  5. 5

    Implement, then verify against the spec

    The agent implements. Then a different pass checks the result against the written criteria — not against its own memory of what it intended to do. Self-review confirms intent. Fresh-context verification finds the gap between intent and behavior.

    I ownReading the diff, running the checks, deciding.
    The agent getsNo credit for "looks right."
    progress-template.md ↓
  6. 6

    Gate before merge

    A read-only QA pass for regressions and contract drift. A separate root-cause pass when something breaks. Both report in a fixed format — pass, fail with evidence, or inconclusive with exactly what could not be checked.

    I ownThe verdict, and the decision to ship.
    The agent getsPermission to read, never to edit.

Worked example

What the loop looks like when the same problem has five different shapes.

One specification, five systems — adapted, not copied

After a security incident, five internal systems needed the same controls: multi-factor authentication, audit logging, password expiry, and account lockout. I wrote the implementation once as a structured specification — requirements, integration points, acceptance criteria, verification steps.

Each system needed it materially reworked. Different authentication flows, different legacy state, different admin surfaces, different definitions of a "user." The specification was the starting point, not a script.

The transferable part was never the code. It was the structure — and the same verification gate at the end of every run.

Outcome: 100+ vulnerabilities remediated and the controls rolled out across all five systems in about a month, with post-deployment fixes and documentation included.

Guardrails

The rules that keep an agent from becoming an unverified author.

Untrusted input is data

Fixture content, user text, and scraped pages are never treated as instructions. Injection attempts are test cases, not commands.

Secrets never round-trip

Credentials are read from the environment, redacted at the boundary, and never echoed into output, logs, or reports.

The tool boundary is explicit

Inputs are named files. The only permitted network destination is the configured provider. Everything else fails closed.

The deterministic core decides

Rules and validation own the canonical result. A model may classify or phrase it, but it is never allowed to change it.

Degrade, do not disappear

When a model is unavailable the system keeps working in a reduced, explicitly labelled mode rather than failing silently.

Report the gap

A check that could not run is reported as inconclusive with the reason. That is not a failure of the process; hiding it would be.

What this method is not

The limits matter as much as the claims.

  • It is not autonomous delivery. I decide, review, and verify every change. The agent writes inside constraints I set; it does not choose the constraints.
  • It does not remove the need to read code. Verification requires understanding what you are accepting. "The tests passed" is not the same as "I know why."
  • Gates catch regressions, not bad design. A wrong specification produces confidently wrong code that passes every check. The quality ceiling is the spec, not the model.
  • It is not model training. I build applications on top of models. No embeddings, no retrieval layer yet, no fine-tuning — and I will say so rather than imply otherwise.
  • Verification is per-change, not per-project. A project can drift across a series of individually correct changes. That is why the handoff pack exists.
