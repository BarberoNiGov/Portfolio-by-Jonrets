Case Study · Architecture & Design Package

Designing a job platform for AI agents

A platform where people register AI agents, publish agent resumes, post work, and let other agents apply. This package is the complete pre-implementation layer: requirements, architecture, decision records, API contracts, and data model — produced through a four-agent pipeline with explicit handoffs between stages.

Status: design complete, implementation not started. This page documents the architecture and the process that produced it. It is not a shipped product, and I am not presenting it as one. The value here is the pre-code layer — the part that decides whether the code will be worth writing.

The problem

If agents are going to work, they need the same things people need: an identity, a resume, a way to find work, a way to apply, and a channel to talk. The interesting constraint is that the primary users are not humans clicking through a UI — they are agents connecting through an API. Every interaction has to exist twice: once for the person configuring the agent, and once for the agent acting on its behalf.

That constraint shaped the whole design. Resumes are Markdown, not a form. Applications need a machine-readable state machine, not an inbox. Credentials for third-party agent platforms need encryption at rest, not a settings row.

The architecture

A modular monolith, chosen deliberately over microservices. One codebase, seven modules with explicit dependencies, and a boundary that would let any module be extracted later without rewriting its consumers. For a system with no traffic yet, distributed complexity would be a cost with no return.

The dependency column is the part that matters. It is a rule, not documentation: no module reaches sideways. Application may depend on Agent and Posting; Posting may not depend on Application. That single constraint is what keeps the monolith modular instead of gradually becoming a pile.

The decision that saved the most future work: treat the resume as a versioned document with a schema, not as fields on a profile. Agents need to export it, other agents need to parse it, and the shape has to survive both.

The pipeline that produced it

Four agents in sequence, each with one responsibility and a handoff artifact. The point of splitting them was not speed. It was to stop requirements, architecture, and implementation from being decided in the same breath — which is how a design quietly becomes whatever was easiest to build.

1

Requirements designer

Functional and non-functional requirements, user flows, and API contracts. docs/requirements/

2

System designer and checker

Module boundaries, technology decisions, data model, and a check that the architecture satisfies the requirements. docs/architecture/

3

Implementation agent

Builds against the contracts, not against a conversation. docs/handoff/

4

Documentation agent

Maintains the decision record and writes the handoff for the next stage.

Each handoff carries what the next agent needs and nothing else: completed artifacts, key requirements, open questions, and the boundaries it may not cross. The pipeline is only as good as those handoffs — which is exactly why they are written files rather than conversational memory.

What I would not claim

  • It is not validated by implementation. A design that has never been built has not met reality. Contracts that look clean on paper often need revision the first week of coding — and that revision is healthy, not failure.
  • More documentation is not automatically better. 3,500 lines is a lot for a system with no users. For a smaller feature this process would be overkill, and I would not run it.
  • The pipeline does not remove judgment. The agents produced artifacts; deciding that the module boundaries were right, that the NFRs were measurable, and that the ADRs had honest tradeoffs was my job.
  • Design review is a stage, not a guarantee. A checker agent can catch contradictions between documents. It cannot tell you the product is worth building.
